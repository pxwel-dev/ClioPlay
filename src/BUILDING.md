# Building ClioPlay

For Windows installation of the included programs, use [WINDOWS.md](../WINDOWS.md)
and the root `Install.cmd` launcher. ARM compilation and the commands below
use Linux/WSL or macOS.

Run commands from this directory. The runtime and builder are independent
of sibling ClioPlay folders.

For the complete maintainer release sequence, including version bumps, ARM
rebuilds, GIFs, publication checks and Git, see the
[release workflow](docs/release-workflow.md).

## ARM programs

Requires Python **3.12+**, Clang with the ARM backend, LLD ELF linker and an archive
tool capable of ARM ELF (LLVM `llvm-ar` on macOS). On macOS:

```sh
brew install python llvm lld
python3 tools/rebuild_arm.py
```

This verifies and installs the three ARM executables into `clio843/` without
refreshing publication or deploying to an SD card. Flags/compiler/input hashes
and ELF checks are written to
`build/*.build.json`. Supply `--clang` / `--linker` if required.

The build also regenerates the splash icon's 8×8 coverage masks from
`tools/build_splash_icon.py`. This needs only Python's standard library; the head
unit composites the small masks directly without a supersampled framebuffer.

This `src/` directory is the canonical development tree inside
`CLIOPLAY-LATEST-VERSION/`. A successful `--install` build also refreshes the
parent folder’s clean-install publication. When UI sources change, use the
rebuild command above, then regenerate the README previews before running
`python3 tools/refresh_latest.py`. The publication check compares the preview
source and executable hashes with the current build.
Documentation/packaging changes need `python3 tools/refresh_latest.py`; use
`python3 tools/refresh_latest.py --check` to verify the maintained delivery against
the current sources and installed programs. The exporter verifies publication integrity and preserves unrelated local additions;
the Git-payload check rejects additions that are not ignored or managed.

The first Unicode-engine build automatically fetches pinned, SHA-256 checked
Debian armel development **headers** into `build/cross-sysroot`. No Debian target
libc, libstdc++ or newer-CPU libgcc is linked. Arithmetic helpers are compiled from
vendored LLVM compiler-rt for ARM7TDMI. HarfBuzz and SheenBidi are vendored too.

Executables are freestanding static ARMv4T ELF32, EABI5 soft float, legacy Linux
OABI syscalls, image base 0x10000 and 64 KiB segment alignment. Build checks reject
dynamic loaders, missing entry points and unresolved symbols. The main executable
has about 10.9 MiB BSS, including the bounded 2 MiB shaping arena and existing map/
route caches. Native font tables are mapped on demand; glyph bitmaps stay on the
card, with a bounded RAM cache. Actual total memory/performance needs hardware
measurement. `--no-map-antialias` is a build-time rendering fallback.

Roads use their own Day/Night palettes and map canvas, separate from HUD/text
colours. Six packed coverage slots retain the local-to-motorway compositing
order. Widths adapt to the rendered zoom: motorway/trunk roads remain prominent,
local roads widen at street-detail zoom, and service roads remain one pixel.
This styling uses the existing single geometry/coverage pass, without extra road
outlines, buffers or map-data changes. The route uses deep raspberry pink by day and
brighter pink at night, separate from blue/teal roads and the orange vehicle
pointer. Its existing three-pixel antialiased stroke is retained.

Thin-road coverage is generated by `tools/build_thin_coverage.py` during the ARM
build. The minor-road class uses Gaussian reconstruction (sigma 0.55 pixels,
nominal width 1.2 pixels); other one-pixel strokes retain pixel-area coverage.
Body/cap lookup tables contain prequantised five-bit mask values. No floating
point, extra framebuffer or image-wide blur runs on the device.
`tests/map-antialias.c` checks independent pixel-area/kernel integration,
subpixel phases, slopes between lookup rows, caps, clipping and subdivision. To capture
matching before/after native framebuffers (Pillow required), preserve a complete
pre-change `clio843/src/` tree outside the publication, then run:

```sh
python3 tools/verify_minor_road_aa.py --maps /path/to/maps \
  --before-source /tmp/before-src/clio040.c --out /tmp/minor-road-aa
```

Captures and host timing reports stay outside the publication. The output uses
the production RGB565 framebuffer; magnified crops use nearest-pixel scaling.


The vehicle pointer uses 28×28 coverage masks for 36 headings, generated by
`tools/build_vehicle_icon.py` during the ARM build. Its outline, orange body and
subtle facet adapt to the current Day/Night palette. All edges are precomputed
with 8×8 supersampling; the device only blends the masks, with no extra map
framebuffer or runtime shape rasterisation. A small pixel-area row filter
foreshortens the pointer in driving view, tracking the live camera tilt through
Explore entry and exit; the settled Explore mask is unchanged.
`tests/vehicle-marker.c` checks every heading, both themes, clipping, no-GPS hiding
and the camera-driven footprint including interrupted reversals.

The roundabout HUD icon uses a 35×35 coverage mask generated by
`tools/build_roundabout_icon.py` during the ARM build. It mirrors for the current
traffic side and keeps the exit number upright. To render controlled Day/Night
examples from the production framebuffer (Pillow required):

```sh
python3 tools/render_roundabout.py --maps navigation-output --out /tmp/roundabout-renders
```

Add `--before-source /tmp/before-src/clio040.c` for a matching baseline from a
preserved source tree. Renders stay outside the publication.

## Navigation and optional font maintenance

```sh
python3 navigation-builder/build_navigation.py
```

This asks for the PBF first and guides region confirmation. Full requirements,
unattended options and camera imports are in
[navigation-builder/README.md](navigation-builder/README.md). Normal builds copy
the bundled, checksum-verified `data/global-fonts.cpf`; no font download or rasterizer
is needed. To regenerate it as a maintainer, install `freetype-py==2.5.1` and
`fonttools==4.60.1` plus a host FreeType library, then run:

```sh
python3 navigation-builder/tools/build_fonts.py --out navigation-builder/data/global-fonts.cpf --cache build/font-cache
```

Font upstream URLs are recorded in the generated report. Retain the resulting
`font-notices.json`, OFL licence and source manifest with the pack.

## Verification

A host C/C++ compiler is required. The framebuffer gallery needs Pillow.
The builder's `.venv` can run `verify_global.py` after its first dependency setup.

```sh
python3 tools/verify_unicode.py
python3 tools/verify_text_cache.py
python3 tools/verify_locales.py
python3 tools/verify_keyboard.py
python3 tools/verify_atlas_viewport.py --maps navigation-output
python3 tools/verify_atlas_qad7.py --maps navigation-output
python3 tools/verify_splash.py
navigation-builder/.venv/bin/python tools/verify_global.py
python3 tools/verify.py --maps /path/to/existing/UK/clio843/maps
```

`verify_unicode.py` links the production shaping engine and tests the actual
2 MiB allocator under host UBSan. It renders 17 native-script examples plus the
Trip screen; checks mixed bidirectional text, native phone handoff/persistence,
unsupported saved-place rejection and UTF‑8-safe rename/delete. These are rendered pixels,
not desktop browser text overlays.

`verify_global.py` builds clearly synthetic metric/imperial PBF fixtures through
the complete pipeline, compares routing against reference queries, exercises
country switching, limits, camera/GPS/average-zone behaviour and installation.
`--real-bundles` additionally uses locally prepared `build/paris` and `build/madrid`
sample bundles. These sample inputs are optional and not part of a source build.
`--cache PATH` reuses an existing coastline cache.

To regenerate the short GIFs embedded in the main README, install Pillow and
use an existing UK map bundle covering Newcastle:

```sh
python3 tools/regenerate_gifs.py --maps /path/to/clio843/maps
```

The tool writes the README GIFs and a provenance manifest to `docs/demo/`.
The renderer uses controlled input and actual remote-handler calls. The phone
destination preview uses a sample message at the daemon/UI boundary. Raw
framebuffers and host executables stay temporary. See [preview notes](docs/demo/README.md).

`verify_keyboard.py` checks all 18 independent language layouts, capital input,
accented/native names, connected remote focus paths, saved choices, soft-key
editing, character bounds, the Hanzi browser and all 11,172 modern Hangul
syllables. It draws every character page/mode in both themes, verifies wrapping
navigation and compares cached text bounds with actual drawn glyphs. Test state
and any captures stay temporary.
`verify_atlas_viewport.py` reproduces device boot ordering against a real UK
atlas covering Newcastle: maps open before GPS, then saved/live fixes and Explore
move beyond the first child pack. It checks every installed core and shared edge,
Day/Night zooms, genuine outside coverage and single-pack edge tolerance. It
uses existing map data read-only and keeps captures temporary.

`verify_atlas_qad7.py` uses the existing UK atlas covering Newcastle to check
mapped and forced-paged QAD7 with a minimum 1 MiB query arena, every regional
index namespace, exact regional route cost, endpoint-cache reset and local suffix
repair. It executes Newcastle–London against the existing UK fixture and checks
route cost/distance, shared work counts and production scheduling, rather than
using a desktop timer as evidence of acceptable 400 MHz performance.
`verify_atlas_destination.py` builds directed synthetic graphs to check unreachable
nearest-road fallback and first-candidate preference through another portal.
Host timings are comparative;
actual head-unit routing/rerouting timing and memory still need a vehicle trial.

Keyboard layouts are baked from `locales/keyboards.json`; normal builds use the
bundled Unicode Pinyin table and need no new SD-card data. See
[locales/README.md](locales/README.md) for input methods and limitations.

`verify.py` exercises a compatible UK pack with the production renderer/key
handler, including routes, polygon holes, controls/animations and 72 bridge
views. No test modifies the supplied source navigation packs.

Publish the contents of the parent `CLIOPLAY-LATEST-VERSION/` folder as the
repository root. Run `python3 tools/refresh_latest.py` and
`python3 tools/verify_publication.py` first. Current programs, default bootstrap,
legacy helper recovery references and available BlueZ sources are included;
firmware, generated maps, caches and personal data stay local.

## Scheduled Auto theme

`clio843/src/boot_theme.h` shares the daily schedule between the splash and UI.
`daystart` and `nightstart` in `prefs.ini` store local minutes after midnight.
Older preferences use Day at 07:00 and Night at 18:00. Invalid or identical
times revert to these defaults.

Choose Auto in Settings, then scroll to Day starts and Night starts.
OK switches between hours and minutes; Left/Right adjusts the highlighted
part. The schedule repeats daily and supports a Day interval crossing midnight.
Day/Night overrides take priority.

Live decisions use the displayed local clock. Before GPS time arrives, the UI
and splash use the unit's UTC clock plus the saved local offset. Automatic
timezone/DST updates also affect the schedule through that offset. With no valid
clock, retain the saved palette, defaulting to Night.

`tests/auto-theme.c` covers exact boundaries, midnight wrap, local offsets,
missing/corrupt preferences, persistence, controls and manual overrides.
`tests/splash.c` verifies the schedule against actual splash framebuffer output.
Both run under UBSan in `tools/verify_ci.py`.

## Boot measurements

The splash draws once, with a procedural softened background and unenclosed,
anti-aliased logo and wordmark. It publishes a checked RGB565 image in `/tmp` for the UI to
consume once. The UI uses one temporary 255 KiB mapping, frees it after the
500 ms cross-fade or input cancellation, and leaves normal services running.
The fade starts at the first completed UI frame and shares the existing 15/5 Hz
presentation cadence; it never sleeps or holds map drawing. A missing, stale or
invalid image falls back to the normal UI. This RAM handoff is runtime state,
not a persistent diagnostic file.

The bootstrap runs AUX initialization first, draws the splash, then starts
Bluetooth and Focus. UI loading overlaps Focus readiness; only the vehicle
daemon waits for `/tmp/cfready` (with an eight-second fallback).
Bluetooth launches the HID listener and starts phone setup immediately, without
waiting for the button-woken remote. The remote listener remains available for
later connections. Service-readiness waits are separate from kernel/firmware boot.

With Settings → Debug log enabled before a cold restart, `clio843/state.log`
and `clio843/bt.log` prefix startup stages with kernel uptime in seconds.
Compare bootstrap entry, AUX completion, splash, UI exec, Focus readiness,
HCI setup, HID listener launch and the Bluetooth boot barrier. These
timestamps use the existing Debug-only logs; no additional persistent boot
status file is created. UI exec is the process handoff, not a first-frame or
remote-ready measurement. Record those visible milestones separately.

For a host breakdown of the actual loaders and first map frame:

```sh
python3 tools/profile_boot.py --maps /path/to/installed/clio843/maps
```

Use `--lat` and `--lon` to select a representative saved map view. Map inputs
are read-only and state/framebuffer outputs are temporary. This reports host
time and page faults, not predicted 400 MHz timings. Atlas loading currently
validates every graph record before the first frame; its cost grows with the
catalog. QAD7 and Unicode loading read headers/catalogs and leave their large
data to be read on demand. Hardware timing is needed before changing validation
or the proven Bluetooth initialization sequence.

## Automatic Navcore download

The clean-card installer downloads the official 8.843 CAB from TomTom, verifies
its pinned SHA-256 and reuses a verified cached copy on subsequent runs. If the
download fails, restore the internet connection and rerun the installer.
Only `ttsystem` and `vehicledaemon` are extracted from the CAB. AUX initialization
is embedded in the custom `ttn` startup script, so `PNDNavigator` is not installed.
The custom `focusd` and other
project helpers are included separately; see [source status](docs/source-status.md).

## Release version

`VERSION` is the release identity. `tools/build_ui.py` generates
`clio843/src/release_version.h` from it and records the version in each binary’s
build report. The Settings footer and UI/Bluetooth startup logs use that generated value. Bootstrap
scripts declare the same `CLIOPLAY_VERSION`. Use
`python3 tools/release_version.py --set 2.1.8` (or the intended new version) to
synchronise the header, bootstrap versions and `bootstrap-SHA256.json`.
Alternatively, `python3 tools/rebuild_arm.py --version 2.1.8` synchronises and
rebuilds in one command.
`python3 tools/release_version.py --check` rejects mismatched labels before
building or publishing. Downloader user agents also read `VERSION`. Map formats,
protocol identifiers and third-party dependency versions are separate.

## Vehicle input and temperature integration

`clio040.c` contains the console FIFO reader and bounded nonblocking VehicleStatus
receiver. The build still ships the same three native programs. `cswd.c` and
`vstatd.c` are source-only contributed references, not additional startup services.
`tests/vehicle-input.c` exercises the integrated code, including both input paths
and temperature providers. The host suite also repeats coordinate/naming/trip,
Explore/zoom/dialog, Bluetooth transport and Settings workflows through the
production console decoder using the default physical bindings. Unix
SOCK_SEQPACKET transport checks are skipped on
hosts without that facility; protocol/FIFO/UI checks still run.

`ttn` selects the mounted card containing `clio843/clio040`, changes to its root
and prepares the console FIFO before Focus/vehicle startup. Both console and
VehicleStatus readers start automatically; valid runtime input selects the
available sources. An idle FIFO does not
claim the evdev knob path. The factory daemon retains its normal vehicle
configuration check. Native card paths are relative to this working directory. Direct experimental launches must
therefore start from the SD-card root too. Bluetooth setup independently resolves
its script directory, retaining early phone connection and the sleeping-remote
behaviour. No always-on boot diagnostics or raw identity logs are introduced.
